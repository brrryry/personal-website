# PP Recommender

<BlogImage
src="/blogs/pp-recommender/recommender.png"
alt="PP Recommender Showcase"
caption="A brief showcase"
source="https://pp.bryanchan.org"
/>

This website takes username inputs and fetches some top/recent osu replays. 
Using these replays, it will recommend maps for the user to play.
 \
\
By definition, it's hard to show the user **why** a certain map is recommended. Since we don't have explicit skill tags, we can't really say "map X has high aim difficulty" or "map Y has high stream difficulty." 
Instead, we rely on the map's properties like star rating, accuracy, length, etc. as a proxy for difficulty. This model "learns" the difficulty of the map. \
\
What we CAN do is show the user which maps have similar embeddings to the maps they've played.

<BlogImage
src="/blogs/pp-recommender/examplerec.png"
alt="Example Recommendation"
caption="Example of a map recommendation."
/>

While there is the obvious con of not being able to explain why a map is recommended, there are a few pros to this approach:
<br />
<BlogList>
<li>
    <b>Reduced Ambiguity</b>: No need to define or worry about "hidden" axes (like readability, technicality, or streaming speed) that might be interpreted differently by different people. The embedding handles this implicitly.
</li>
<li>
    <b>Simpler Architecture</b>: We can use a simpler, "axis-free" autoencoder architecture (like the Denoising Autoencoder) instead of a more complex model with multiple decoders for each skill axis (e.g., a stacker autoencoder).
</li>
<li>
    <b>Data Flexibility</b>: Since we are not relying on pre-defined axis labels, we can train the model on various datasets (e.g., user replays, map characteristics) without needing to map them to specific axes first.
</li>
<li>
    <b>Strong Foundation</b>: A subsequent axis model can be added on TOP of this model, allowing us to still get the explainability while using the vector embeddings as a base for the model.
</li>
<li>
    <b>Modded Compatability</b>: This model can learn which maps are likely to have certain mods based on their structure, something that is difficult to do with explicit axes. It can also recommend maps with mods that the user hasn't played before.
</li>
</BlogList>

In a way, this kind of model has higher potential for better recommendations since we don't rely on multiple subjective axis definitions. \

## 1. Data Processing
Osu! beatmap files (.osu files) have a specific format. From them, you can extract all the hit objects (circles, sliders and spinners).
You can also get all the timing points (determines bpm, offset, slider velocity, etc.). \
\
To put this data into a nice list of numbers, I did the following:

<BlogList>
<li>For each object, get the position and time.</li>
<li>Find the differences in position and time between consecutive objects. Now we have $\Delta x$ and $\Delta y$ values.</li>
<li>Get the type of object and its details.</li>
<li>Also put in the overall map stats (e.g. OD, AR, HP, CS).</li>
</BlogList>

<br />
All in all, I had a 13-dimensional vector. 
<br />
<BlogList>
<li>$\Delta x$ - change in x position</li>
<li>$\Delta y$ - change in y position</li>
<li>$\Delta t$ - change in time</li>
<li>is_circle - 1 if circle, 0 otherwise</li>
<li>is_slider - 1 if slider, 0 otherwise</li>
<li>is_spinner - 1 if spinner, 0 otherwise</li>
<li>slider_velocity - slider velocity</li>
<li>slider_linearity - slider linearity</li>
<li>slider_bezier - slider bezier</li>
<li>OD - overall difficulty</li>
<li>AR - approach rate</li>
<li>HP - health drain</li>
<li>CS - circle size</li>
</BlogList>
<br />

I took a maximum of 2000 objects per map to keep the padding and training time reasonable. Thus, our input is a matrix of size 2000x13.

<span id="vae-math"/>
## 2. <a href="https://en.wikipedia.org/wiki/Variational_autoencoder" target="_blank">Variational Autoencoder (VAE) Math</a> <sub>[\[3\]](#citation3)</sub>
If you want to skip all the math, click <a href="#vae-model">here</a>.\
\
The variational autoencoder is a model that was introduced around 2013 by Diedrik P. Kingma and Max Welling. The paper can be found <a href="https://arxiv.org/abs/1312.6114" target="_blank">here</a> <sub>[\[4\]](#citation4)</sub>. \
\
Standard autoencoders have two parts: an encoder, and a decoder. 
The encoder turns an input vector (list of numbers) into a compressed vector (basically shrinking the input vector in size, i.e. dimensions).
The decoder tries to reconstruct the original input from this compressed vector.
An easy way to think about it is trying to compress a file into a zip file, and then decompressing the zip file. 
(Note: This is not actually how zip files work, but it's a good analogy.)

<BlogImage
src="/blogs/pp-recommender/autoencoder.webp"
alt="Autoencoder Diagram"
caption="A diagram of an autoencoder (NOT A VAE) from GeeksforGeeks [5]."
source="https://www.geeksforgeeks.org/deep-learning/types-of-autoencoders/"
/>

In most cases, both the encoder and decoder are defined as multilayer perceptrons (fancy term for a type of neural network).
Let's use a more mathematical approach (this will make it easier to compare VAEs later). 

<br />

### 1. Mathematical Formulation of Autoencoders


Given an input vector $x \in \mathbb{R}^d$, we create the encoder function $f_\phi$ which maps $x$ to a compressed vector $z \in \mathbb{R}^d$ ($d << D$). \
\
(The notation $f_\phi$ means that we have a function $f$ that depends on parameters $\phi$. In this case, $\phi$ represents the weights and biases of the neural network.)

$$
z = f_\phi(x)
$$

We use the decoder function $g_\theta$ to reconstruct an estimation of the original vector $\hat{x}$.

$$
\hat{x} = g_\theta(z) = g_\theta(f_\phi(x))
$$

Our goal is to learn parameters $\phi$ and $\theta$ such that $\hat{x} \approx x$.
In the event of continuous output space (like our map features), we can define our reconstruction loss $L_{rec}(\phi, \theta)$ using Mean Squared Error <sub>[\[20\]](#citation20)</sub> (a typical deterministic loss function for regression tasks):

$$
L_{rec}(\phi, \theta) = ||x - \hat{x}||^2_2
$$

Autoencoders can be trained like any other neural network, so gradient descent is typically used.

<br />

That's how standard autoencoders work, but variational autoencoders are a bit different.
Variational Autoencoders approach learning with a more probabilistic approach (specifically using <a href="https://en.wikipedia.org/wiki/Bayesian_inference" target="_blank">Bayesian Inference</a> <sub>[\[6\]](#citation6)</sub>). 

<br />

### 2. <a href="https://en.wikipedia.org/wiki/Maximum_likelihood_estimation" target="_blank">Maximum Likelihood Estimation</a> <sub>[\[7\]](#citation7)</sub> - A Primer

<details className="bg-purple-500/5 dark:bg-purple-500/10 border border-purple-500/10 rounded-xl p-4 my-6 cursor-pointer">
  <summary className="font-semibold text-purple-800 dark:text-purple-200 select-none">📊 Click here for more info!</summary>

  Small tangent (I promise it's relevant), but do you know how statistics like sample mean and sample standard deviation are derived?
  I'm sure you've heard of them before. \
  \
  If you have a <b><i><a href="https://en.wikipedia.org/wiki/Independent_and_identically_distributed_random_variables" target="_blank">i.i.d</a></i></b> <sub>[\[12\]](#citation12)</sub> normally distributed <sub>[\[18\]](#citation18)</sub> random sample of data, say points $x_1, x_2, \dots, x_n$, we can calculate the sample mean $\bar{x}$ as:

  $$
  \bar{x} = \frac{1}{n} \sum_{i=1}^{n} x_i
  $$

  This formula is beautifully simple, and it's built on the idea that we can maximize the chance of getting our sample data given a certain distribution. \
  \
  As an analogy, think of flipping a coin. If the coin is truly fair (50/50), what's the probability of getting 3 heads in a row? 
  The same idea goes here - if the true population mean is $\mu$, what's the probability of getting our sample data? We want to choose a $\mu$ that maximizes this probability. \
  \
  To figure this out, we use the Maximum Likelihood Estimation (MLE) method - a method for estimating the parameters of a statistical model given an observed dataset. \
  \
  I'll spare the calculus lesson (do you know derivatives/integrals?), but let's go through an example. \
  \
  We will make an estimation of the population mean $\mu$. We will call our estimate $\hat{\mu}$ (mu-hat). \
  \
  We look at the likelihood of observing our data given the parameter $\mu$ (the chance that we get this data if the mean is $\mu$). 
  If each data point is sampled independently, then the likelihood of observing all of our data is the product of the likelihoods of observing each data point.
  $$ 
  L(\mu) = P(X | \mu) = \prod_{i=1}^{n} \frac{1}{\sqrt{2\pi\sigma^2}} e^{-\frac{(x_i - \mu)^2}{2\sigma^2}}
  $$

  The formula above looks ridiculous, and it looks like I pulled it out of thin air, but it's the normal probabilty density function.
  Now that I'm writing this, I realize that there's a lot to explain...oof... \
  \
  Typically, we use log-likelihood (taking the logarithm) to make computations easier.

  $$
  \begin{align}
  l(\mu) &= log(\prod_{i=1}^{n} \frac{1}{\sqrt{2\pi\sigma^2}} e^{-\frac{(x_i - \mu)^2}{2\sigma^2}}) \\
  &= \sum_{i=1}^{n} log(\frac{1}{\sqrt{2\pi\sigma^2}}) + log(e^{-\frac{(x_i - \mu)^2}{2\sigma^2}}) \\
  &= \sum_{i=1}^{n} -log(\sqrt{2\pi\sigma^2}) - \frac{(x_i - \mu)^2}{2\sigma^2}
  \end{align}
  $$

  Now, how do we maximize $l(\mu)$? We find the **critical point** (calculus 1)! 
  Since we know that the function is concave (you can verify this by taking the Hessian of the function, but just take my word for it...), the critical point is guaranteed to be the maximum. \
  \
  By differentiating the log-likelihood function with respect to $\mu$, we get:

  $$
  \begin{align}
  \frac{d}{d\mu} [l(\mu)] &= \frac{d}{d\mu} \left[ \sum_{i=1}^{n} -log(\sqrt{2\pi\sigma^2}) - \frac{(x_i - \mu)^2}{2\sigma^2} \right] \\
  &= \sum_{i=1}^{n} \frac{d}{d\mu} [-log(\sqrt{2\pi\sigma^2})] - \frac{d}{d\mu} \left[ \frac{(x_i - \mu)^2}{2\sigma^2} \right] \\
  &= 0 - \frac{1}{2\sigma^2} \sum_{i=1}^{n} 2(x_i - \mu)(-1) \\
  &= \frac{1}{\sigma^2} \sum_{i=1}^{n} (x_i - \mu)
  \end{align}
  $$

  And by setting it to 0, we solve for our estimator $\hat{\mu}$:

  $$
  \begin{gathered}
  \frac{1}{\sigma^2} \sum_{i=1}^{n} (x_i - \hat{\mu}) = 0 \\
  \sum_{i=1}^{n} (x_i - \hat{\mu}) = 0 \\
  \sum_{i=1}^{n} x_i - \sum_{i=1}^{n} \hat{\mu} = 0 \\
  \sum_{i=1}^{n} x_i = n \hat{\mu} \\
  \hat{\mu} = \frac{1}{n} \sum_{i=1}^{n} x_i = \bar{x}
  \end{gathered}
  $$

  Therefore, our best estimation for the population mean is $\bar{x}$, commonly known as the **sample mean**! \
  \
  I wish I learned how these formulas were derived back when I first took statistics...it's honestly fascinating. 
</details>

### 3. <a href="https://en.wikipedia.org/wiki/Bayesian_inference" target="_blank">Bayesian Inference</a> <sub>[\[6\]](#citation6)</sub> - Another Primer

<details className="bg-purple-500/5 dark:bg-purple-500/10 border border-purple-500/10 rounded-xl p-4 my-6 cursor-pointer">
  <summary className="font-semibold text-purple-800 dark:text-purple-200 select-none">🔮 Click here for more info!</summary>

  To understand VAEs, we must first understand how <a href="https://en.wikipedia.org/wiki/Bayesian_inference" target="_blank">Bayesian Inference</a> <sub>[\[6\]](#citation6)</sub> works in the context of statistics. \
  \
  This technique involves using a prior belief (a hypothesis $H$), and using new evidence (data $D$) to update our beliefs (the posterior probability $P(H|D)$). \
  \
  We begin with <a href="https://en.wikipedia.org/wiki/Bayes%27_theorem" target="_blank">Bayes' Theorem</a> <sub>[\[8\]](#citation8)</sub> - a way to calculate posterior probabilities. 
  Bayes' Theorem is defined as:

  $$
   P(H|D) = \frac{P(D|H)P(H)}{P(D)} 
  $$

  Where:

  - $H$: Hypothesis - A statement or proposition about the world
  - $D$: Data - The observed evidence
  - $P(H|D)$: Posterior Probability - The probability of the hypothesis being true given the data
  - $P(D|H)$: Likelihood - The probability of the observed data given the hypothesis
  - $P(H)$: Prior Probability - The probability of the hypothesis being true before observing the data
  - $P(D)$: Evidence - The probability of the observed data

  <br />

  In MLE, we treated the hypothesis (or parameters) as fixed, unknown constants, and our goal was to find the single value that maximized the likelihood $P(D|H)$ of our observed data (for example, finding the MLE of $\mu$ - a CONSTANT). \
  \
  In the Bayesian framework, however, we treat the hypothesis (i.e. $\mu$) itself as a random variable. We assign it a **prior** probability distribution $P(\mu)$ (representing our beliefs before seeing any data). For instance, maybe we think that coin flips are usually fair, so we assign a prior probability distribution that is peaked around $\mu = 0.5$ (we do not say that $\mu$ IS 0.5 - this is the difference). 

  <br />

  We then update our beliefs by multiplying the prior by the likelihood $P(D|\mu)$ to get the **posterior** probability distribution $P(\mu|D)$ using Bayes' Theorem. \
  \
  Here's an interesting way to think about it: **MLE is basically Bayes' rule with a uniform prior distribution ($P(H)$ = 1 for all H).**

</details>

<br />

### 4. Inferring Posterior Distributions (Primers Over!)

We apply the Bayesian framework to infer the posterior probability distribution $P(z|x)$: 

$$ 
P(z|x) = \frac{P(x|z)P(z)}{P(x)} 
$$

Where:

- $P(z|x)$: Posterior Probability - The probability of the latent variable given the observed data
- $P(x|z)$: Likelihood - The probability of the observed data given the latent variable
- $P(z)$: Prior Probability - The probability of the latent variable before observing the data
- $P(x)$: Evidence - The probability of the observed data

<br />

At the same time, we want to infer the posterior distribution $P(z|x)$ to find the latent representation $z$ for any given data point $x$. \
\
(TLDR: we want to maximize the likelihood of our vector $x$ while finding a compressed form $z$ that captures the most important features in $x$.)\
\
To apply this to our autoencoder, we parameterize the generative model (the decoder) with parameters $\theta$. Thus, our model's likelihood is $P_\theta(x|z)$ and the joint distribution is $P_\theta(x, z) = P_\theta(x|z)P(z)$ (assuming a fixed prior $P(z)$). \
\
As mentioned earlier, the denominator, $P_\theta(x)$, is the model **evidence**. It represents the probability of generating our observed data under all possible latent configurations:

$$
P_\theta(x) = \int P_\theta(x, z) dz = \int P_\theta(x|z) P(z) dz
$$

The problem is that computing this integral is ridiculously hard to do for complex, high-dimensional datasets. The reason for this is that we would have to search over the entire infinite space of possible latent variables $z$ to compute the integral.
If our $z$ was 1-dimensional, computation wouldn't be hard. However, compressed vectors are often 128 or 256 dimensional, making the integral impossible to compute. \
\
You could try to differentiate the log-likelihood with respect to the parameters $\theta$ directly, but computing that gradient requires taking an expectation over the true posterior $P_\theta(z|x)$—which is the very thing we are trying to infer in the first place (catch 22)! \
\
Because we cannot calculate $P_\theta(x)$, we cannot compute the true model posterior $P_\theta(z|x)$ directly using Bayes' Theorem. \
\
How do we find $z$ (our compressed vector) AND $\theta$ (our decoder parameters) then?? 

<br />

### 5. <a href="https://en.wikipedia.org/wiki/Variational_inference" target="_blank">Variational Inference</a> <sub>[\[9\]](#citation9)</sub>: Approximating the Unknowable

Since we can't calculate the true model posterior $P_\theta(z|x)$, we have to approximate it.
We use a technique called **Variational Inference** to approximate this intractable posterior distribution (the crazy integral from before). \
\
We do this by introducing a new, simpler distribution $q_\phi(z|x)$ (called the **variational posterior** or the **recognition model**), which is parameterized by weights $\phi$. In practice, this distribution is parameterized by our **encoder network**. \
\
We want to make $q_\phi(z|x)$ as close as possible to the true model posterior $P_\theta(z|x)$. In probability theory, we measure the difference (or divergence) between two probability distributions using the <a href="https://en.wikipedia.org/wiki/Kullback%E2%80%93Leibler_divergence" target="_blank">**Kullback-Leibler (KL) Divergence**</a> <sub>[\[10\]](#citation10)</sub>. \
\
On a surface level, we are trying to find the difference between our approximation of the posterior distribution and the REAL posterior distribution.
We do this by integrating over our simpler distribution and multiplying it by the ratio of the two distributions (inside a log). Optimally, if the two distributions are identical, the KL divergence becomes $log(1) = 0$.
$$
D_{KL}(q_\phi(z|x) \parallel P_\theta(z|x)) = \int q_\phi(z|x) \log \left( \frac{q_\phi(z|x)}{P_\theta(z|x)} \right) dz
$$

The KL divergence is always greater than or equal to 0 ($D_{KL} \geq 0$). If you'd like to know more about why, check the wiki article (I don't want to explain it LOL). \
\
Our goal is now to minimize this divergence. It can serve as our loss function! But...\
\
Hollup. The equation for KL divergence still contains the intractable true posterior $P_\theta(z|x)$ inside the log. That was the whole problem...so how do we minimize it? \
\
Well...we don't. Instead, we rearrange the equation to isolate the evidence $P_\theta(x)$ (which is equivalent to $P_\phi(x)$ for our purposes).

<br />

### 6. The Pivot: <a href="https://en.wikipedia.org/wiki/Evidence_lower_bound" target="_blank">Evidence Lower Bound (ELBO)</a> <sub>[\[11\]](#citation11)</sub>

Haha, ELBO. Pronounced like elbow. Like, pivot...elbow...\
\
ok. anyways. \
\
Given the parameters of our encoder ($\phi$) and decoder ($\theta$), we can use the following formula:

$$
\mathrm{ELBO}(\theta, \phi; x) = \mathbb{E}_{q_\phi(z|x)} \left[ \log P_\theta(x, z) - \log q_\phi(z|x) \right]
$$

The ELBO is a lower bound on the model evidence $\log P_\theta(x)$ (and thus also a lower bound on the KL divergence).

<details className="bg-purple-500/5 dark:bg-purple-500/10 border border-purple-500/10 rounded-xl p-4 my-6 cursor-pointer">
  <summary className="font-semibold text-purple-800 dark:text-purple-200 select-none">📐 Show the math derivation!</summary>

  Let's expand the logarithm of the ratio inside the KL divergence:

  $$
  \log \left( \frac{q_\phi(z|x)}{P_\theta(z|x)} \right) = \log q_\phi(z|x) - \log P_\theta(z|x)
  $$

  Now, using Bayes' Theorem, we can write $\log P_\theta(z|x)$ as:

  $$
  \log P_\theta(z|x) = \log \left( \frac{P_\theta(x, z)}{P_\theta(x)} \right) = \log P_\theta(x, z) - \log P_\theta(x)
  $$

  Substituting this back into the log ratio:

  $$
  \log q_\phi(z|x) - \log P_\theta(z|x) = \log q_\phi(z|x) - \log P_\theta(x, z) + \log P_\theta(x)
  $$

  Now, let's plug this back into the KL divergence formula (expressing it as an expectation):

  $$
  D_{KL}(q_\phi(z|x) \parallel P_\theta(z|x)) = \mathbb{E}_{q_\phi(z|x)} \left[ \log q_\phi(z|x) - \log P_\theta(x, z) + \log P_\theta(x) \right]
  $$

  Since the expectation is with respect to $z$, and $\log P_\theta(x)$ does not depend on $z$ (it is a constant relative to $z$), we can pull $\log P_\theta(x)$ out of the expectation:

  $$
  D_{KL}(q_\phi(z|x) \parallel P_\theta(z|x)) = \mathbb{E}_{q_\phi(z|x)} \left[ \log q_\phi(z|x) - \log P_\theta(x, z) \right] + \log P_\theta(x)
  $$

  Let's rearrange this equation to solve for the log-evidence $\log P_\theta(x)$:

  $$
  \log P_\theta(x) = \mathbb{E}_{q_\phi(z|x)} \left[ \log P_\theta(x, z) - \log q_\phi(z|x) \right] + D_{KL}(q_\phi(z|x) \parallel P_\theta(z|x))
  $$

  Because the KL divergence is always non-negative ($D_{KL} \geq 0$), the expectation term on the left acts as a lower bound on the log-evidence. We call this the **Evidence Lower Bound**, or **ELBO**:

  $$
  \mathrm{ELBO}(\theta, \phi; x) = \mathbb{E}_{q_\phi(z|x)} \left[ \log P_\theta(x, z) - \log q_\phi(z|x) \right]
  $$

</details>

The core relationship between our true log-likelihood and the ELBO is:

$$
\log P_\theta(x) \geq \mathrm{ELBO}(\theta, \phi; x)
$$

This is a beautiful mathematical trick. By maximizing the ELBO:

<BlogList>
  <li>We maximize the log-likelihood of our model generating real data $\log P_\theta(x)$.</li>
  <li>We implicitly minimize the KL divergence $D_{KL}(q_\phi(z|x) \parallel P_\theta(z|x))$, forcing our approximate posterior to converge to the true posterior.</li>
</BlogList>

<br />

#### Connecting ELBO Back to MLE
If this feels a bit detached from the MLE primer we went through earlier, here is the connection: our high-level objective in training the VAE (specifically the decoder) is to find parameters $\theta$ that maximize the likelihood of the training data:

$$
\max_\theta \log P_\theta(x)
$$

This is exactly **Maximum Likelihood Estimation**! 
Because we cannot optimize $\log P_\theta(x)$ directly due to the intractable integration over $z$, we use the ELBO as a proxy goal (that's what the last few sections were about). 
When we maximize the ELBO with respect to $\theta$ and $\phi$, we are performing approximate MLE on our neural network parameters.

<br />

### 7. ELBO Loss Analysis

Let's expand the joint probability $P_\theta(x, z) = P_\theta(x|z) P(z)$ inside the ELBO definition to see how it maps to an autoencoder structure:

$$
\begin{align}
\mathrm{ELBO}(\theta, \phi; x) &= \mathbb{E}_{q_\phi(z|x)} \left[ \log \left( P_\theta(x|z) P(z) \right) - \log q_\phi(z|x) \right] \\
&= \mathbb{E}_{q_\phi(z|x)} \left[ \log P_\theta(x|z) + \log P(z) - \log q_\phi(z|x) \right] \\
&= \mathbb{E}_{q_\phi(z|x)} \left[ \log P_\theta(x|z) \right] - \mathbb{E}_{q_\phi(z|x)} \left[ \log q_\phi(z|x) - \log P(z) \right] \\
&= \mathbb{E}_{q_\phi(z|x)} \left[ \log P_\theta(x|z) \right] - D_{KL}(q_\phi(z|x) \parallel P(z))
\end{align}
$$

When training a neural network, we usually minimize a loss function, so we define the VAE loss as the negative ELBO:

$$
L_{\mathrm{VAE}}(\theta, \phi; x) = - \mathbb{E}_{q_\phi(z|x)} \left[ \log P_\theta(x|z) \right] + D_{KL}(q_\phi(z|x) \parallel P(z))
$$

Let's dissect these two distinct terms:

<BlogList>
<li>
  <b>Reconstruction Term</b>: $- \mathbb{E}_{q_\phi(z|x)} \left[ \log P_\theta(x|z) \right]$ <br />
  This term measures how well the decoder ($P_\theta(x|z)$) reconstructs the original input $x$ from a latent vector $z$ sampled from the encoder ($q_\phi(z|x)$). Under a Gaussian assumption for continuous inputs, this expectation is equivalent to Mean Squared Error (MSE) - the distance formula.
</li>
<li>
  <b>KL Regularization Term</b>: $D_{KL}(q_\phi(z|x) \parallel P(z))$ <br />
  This term measures how much our approximate posterior $q_\phi(z|x)$ deviates from the prior distribution $P(z)$. By choosing a simple standard normal prior, $P(z) = \mathcal{N}(0, I)$, we force the encoder to map inputs to a smooth, continuous, and centered region of the latent space, preventing overfitting.
</li>
</BlogList>

<br />

The difference between these two terms represents a trade-off. If we minimize the reconstruction term, the model will prioritize accurate reconstruction, potentially ignoring the regularization term and leading to overfitting.
On the other hand, if we minimize the regularization term, the model will prioritize a smooth latent space, potentially sacrificing reconstruction accuracy.

<br />

### 8. The Reparameterization Trick

OK, but there's another obstacle. To train the encoder and decoder end-to-end, gradients must flow backwards through the network: from the reconstruction loss, through the latent code $z$, and into the encoder. \
\
But $z$ is sampled stochastically from our simplified posterior: $z \sim q_\phi(z|x)$. \
\
Because sampling is a random process, it is not differentiable...so you can't get a gradient from it. 
That means backpropagation cannot calculate how a small change in the encoder's parameters ($\phi$) affects the sample $z$.\
\
To solve this, Kingma and Welling introduced the **Reparameterization Trick**. 

Instead of sampling directly from $\mathcal{N}(\mu, \sigma^2)$, we sample a noise variable $\epsilon$ from a standard normal distribution:

$$
\epsilon \sim \mathcal{N}(0, I)
$$

Then, we calculate $z$ (our compressed vector) using a deterministic, differentiable formula:

$$
z = \mu + \sigma \odot \epsilon
$$

Where $\odot$ represents element-wise multiplication. By shifting the randomness to $\epsilon$ (which doesn't depend on the encoder's parameters), the pathway from the encoder's outputs ($\mu$ and $\sigma$) to $z$ becomes fully differentiable!

<br />

### 9. <a href="https://arxiv.org/abs/2002.05709" target="_blank">Contrastive Learning and InfoNCE Loss</a> <sub>[\[13\]](#citation13)</sub>

OK, we're almost done with the math and theory part of this project. Let's talk about contrastive learning. \
\
I actually first learned about this in my <a href="https://web.stevens.edu/catalog/archive/2024-2025/en/catalog/academic-catalog/courses/cs-computer-science/500/cs-560.html" target="_blank">Statistical Machine Learning</a> class. I never thought I'd actually use it... \
\
Contrastive learning aims to pull positive pairs (two augmented versions of the same beatmap) closer together in latent space while pushing negative pairs (different beatmaps in the batch) further apart.
It's a discriminator, but for data. It tries to distinguish positive pairs from negative pairs. This helps prevent a VAE from collapsing (mapping everything to a single point in latent space). \
\
First, we need a good augmented beatmap dataset. We apply stochastic data augmentations (such as small spatial/temporal shifts, scaling, and random noise) to create two augmented views per map, going from $N$ to $2N$ samples. 
<br />
For a positive pair of normalized latent projections $(\mathbf{z}_i, \mathbf{z}_j)$, the **InfoNCE Loss** is defined as:

$$
L_{i, j} = - \log \frac{\exp\left( \frac{\mathrm{sim}(\mathbf{z}_i, \mathbf{z}_j)}{\tau} \right)}{\sum_{k=1, k \neq i}^{2N} \exp\left( \frac{\mathrm{sim}(\mathbf{z}_i, \mathbf{z}_k)}{\tau} \right)}
$$

Where:
<BlogList>
  <li><b>Cosine Similarity</b>: $\mathrm{sim}(\mathbf{z}_i, \mathbf{z}_j) = \frac{\mathbf{z}_i^\top \mathbf{z}_j}{\|\mathbf{z}_i\|_2 \|\mathbf{z}_j\|_2}$ measures the directional alignment between vectors in hyperspace. It is a very common function to use in machine learning.</li>
  <li><b>Temperature ($\tau$)</b>: A hyperparameter that controls the scale of penalties for hard negative pairs. Higher temperatures make the distribution softer, while lower temperatures make it sharper.</li>
  <li><b>Denominator Sum</b>: Computes similarity against all other $2N - 1$ augmented maps in the batch, treating them as negative pairs. Very contrastive.</li>
</BlogList>

<br />

By incorporating InfoNCE loss into our total VAE loss:

$$
L_{\text{total}} = L_{\text{recon}} + \beta \cdot D_{\text{KL}} + \lambda_{\text{contrast}} \cdot L_{\text{InfoNCE}}
$$

The model learns an embedding space where beatmaps with similar structural rhythms and placement properties naturally cluster together without needing manual skill axis labels!

#### Encoder
The encoder processes input tensors of shape `(batch_size, 13, 2000)` through 5 sequential 1D convolutional blocks. Each block applies a `Conv1d`, `BatchNorm1d`, `LeakyReLU(0.1)`, and `Dropout`:
<br />
<BlogList>
  <li><b>Conv Block 1</b>: 13 $\rightarrow$ 32 channels, kernel 5, stride 2, padding 2</li>
  <li><b>Conv Block 2</b>: 32 $\rightarrow$ 64 channels, kernel 5, stride 2, padding 2</li>
  <li><b>Conv Block 3</b>: 64 $\rightarrow$ 128 channels, kernel 5, stride 2, padding 2</li>
  <li><b>Conv Block 4</b>: 128 $\rightarrow$ 256 channels, kernel 5, stride 2, padding 2</li>
  <li><b>Conv Block 5</b>: 256 $\rightarrow$ 256 channels, kernel 5, stride 5, padding 0</li>
</BlogList>
<br />

We use dynamic sequence masking to ensure that maps that have less than 2000 hit objects are still processed correctly (the model will not train on a bunch of padded zeros).
After adaptive average pooling (taking the average along the sequence dimension) to pool size 16, 
two separate linear layers output the Gaussian mean ($\boldsymbol{\mu}$) and log-variance ($\log \boldsymbol{\sigma}^2$) vectors for a **128-dimensional latent space**:

$$
\boldsymbol{\mu} = W_\mu \cdot \text{Pooled}(\mathbf{H}) + b_\mu, \quad \log \boldsymbol{\sigma}^2 = W_{\sigma^2} \cdot \text{Pooled}(\mathbf{H}) + b_{\sigma^2}
$$

#### Reparameterization Trick
Now, we use that trick from the math part.
Using the predicted $\boldsymbol{\mu}$ and $\log \boldsymbol{\sigma}^2$, the latent vector $\mathbf{z} \in \mathbb{R}^{128}$ is sampled as a continuous function of the input via standard normal noise $\boldsymbol{\epsilon} \sim \mathcal{N}(\mathbf{0}, \mathbf{I})$:

$$
\mathbf{z} = \boldsymbol{\mu} + \exp\left(\frac{1}{2} \log \boldsymbol{\sigma}^2\right) \odot \boldsymbol{\epsilon}
$$

#### Decoder
The decoder maps $\mathbf{z}$ back to shape `(batch_size, 13, 2000)` using a linear projection layer followed by 5 upsampling blocks:

<BlogList>
  <li>Linear projection: $128 \rightarrow 256 \times 16$ tensor</li>
  <li><b>Upsample Block 1</b>: Linear interpolation to size 125 $\rightarrow$ Conv1d(256 $\rightarrow$ 256)</li>
  <li><b>Upsample Block 2</b>: Linear interpolation to size 250 $\rightarrow$ Conv1d(256 $\rightarrow$ 128)</li>
  <li><b>Upsample Block 3</b>: Linear interpolation to size 500 $\rightarrow$ Conv1d(128 $\rightarrow$ 64)</li>
  <li><b>Upsample Block 4</b>: Linear interpolation to size 1000 $\rightarrow$ Conv1d(64 $\rightarrow$ 32)</li>
  <li><b>Upsample Block 5</b>: Linear interpolation to size 2000 $\rightarrow$ Conv1d(32 $\rightarrow$ 13)</li>
</BlogList>

<br />
The output of the decoder is our reconstruction $\mathbf{\hat{X}}$, which we compare to the original input $\mathbf{X}$ using Mean Squared Error. 

<br />

### 3. Contrastive VAE Loss Function

To enforce clustering of semantically similar beatmap patterns while maintaining smooth latent generation, the network is trained using a composite **Contrastive VAE** objective:

$$
L_{\text{total}} = L_{\text{MSE}}(\mathbf{X}, \mathbf{\hat{X}}) + \beta \cdot D_{\text{KL}}\!\left(\mathcal{N}(\boldsymbol{\mu}, \boldsymbol{\sigma}^2) \parallel \mathcal{N}(\mathbf{0}, \mathbf{I})\right) + \lambda_{\text{contrast}} \cdot L_{\text{InfoNCE}}(\mathbf{z}_1, \mathbf{z}_2)
$$

Where:
<BlogList>
  <li><b>Reconstruction Loss ($L_{\text{MSE}}$)</b>: Mean Squared Error between the original beatmap feature matrix $\mathbf{X}$ and the decoded matrix $\mathbf{\hat{X}}$.</li>
  <li><b>KL Divergence ($D_{\text{KL}}$)</b>: Penalizes posterior deviation from the prior $\mathcal{N}(\mathbf{0}, \mathbf{I})$, multiplied by weighting factor $\beta$.</li>
  <li><b>Contrastive Loss ($L_{\text{InfoNCE}}$)</b>: Measures similarity between augmented view pairs $(\mathbf{z}_1, \mathbf{z}_2)$ generated via spatial/temporal jittering, scaling, and Gaussian noise.</li>
</BlogList>

<br />

## 4. Recommendation Model (Theory)

Again, if you want to skip this, you can click <a href="#als-implementation">here</a>. \
\
Now that we have low-dimensional, content-aware VAE beatmap representations ($\mathbf{z}_i$), how do we generate personalized recommendations for an osu! player based on their actual play history?

Enter **Implicit Alternating Least Squares (iALS)** Matrix Factorization <sub>[\[15\]](#citation15)</sub>.

<br />

### 1. Implicit Feedback: Preference vs. Confidence

In standard recommendation systems (e.g., movie ratings), users provide **explicit feedback**—giving a rating $r_{ui} \in \{1, 2, 3, 4, 5\}$. In osu!, however, players don't explicitly rate beatmaps. We only observe **implicit feedback**: play counts, retry counts, score submissions, and replay mastery scores.\
\
We model this by splitting user-map interactions into two concepts:

<BlogList>
  <li>
    <b>Binary Preference ($p_{ui}$)</b>: Indicates whether user $u$ has played beatmap $i$.
    $$p_{ui} = \begin{cases} 1 & \text{if } r_{ui} > 0 \\ 0 & \text{if } r_{ui} = 0 \end{cases}$$
  </li>
  <li>
    <b>Confidence ($c_{ui}$)</b>: Measures how confident we are in that preference based on interaction magnitude (e.g., mastery score or play weight).
    $$c_{ui} = 1 + \alpha \cdot \text{mastery}_{ui}$$
    Unobserved pairs ($r_{ui} = 0$) are assigned $p_{ui} = 0$ with a baseline confidence of $c_{ui} = 1.0$. A higher mastery score increases $c_{ui}$, signaling stronger positive preference.
  </li>
</BlogList>

<br />

We define the "mastery score" of the osu map arbitrarily, and I may change it in the future. For now, this is what it is:

$$
\mathrm{mastery}_{ui} = \mathrm{accuracy}^3 * max\left(0, 1 - \frac{\mathrm{misses}}{{\mathrm{total objects}}}\right) * \frac{\mathrm{max combo}}{\mathrm{total objects}}
$$

<br />

This implicit data is very valuable!


<br />

### 2. The iALS Objective Loss Function & User Vector Projection

We map each user $u$ to a **vector** $\mathbf{x}_u \in \mathbb{R}^f$ and each beatmap $i$ to a **vector** $\mathbf{y}_i \in \mathbb{R}^f$ (with $f = 64$). \
\
Originally, the matrices $X$ and $Y$ are random. The steps below are used to optimize these matrices.

<BlogList>
<li>Keep $Y$ fixed, optimize for $\mathbf{x}_u$ via our loss function.</li>
<li>Keep $X$ fixed, optimize for $\mathbf{y}_i$ via our loss function.</li>
<li>Repeat until convergence.</li>
</BlogList>

Unlike explicit factorization, we optimize the cost function over **all** $N \times M$ user-item pairs (including all unobserved pairs):

$$
\mathcal{L}(X, Y) = \sum_{u=1}^N \sum_{i=1}^M c_{ui} \left( p_{ui} - \mathbf{x}_u^\top \mathbf{y}_i \right)^2 + \lambda \left( \sum_{u=1}^N \|\mathbf{x}_u\|_2^2 + \sum_{i=1}^M \|\mathbf{y}_i\|_2^2 \right)
$$

Where $\lambda$ is the L2 regularization <sub>[\[17\]](#citation17)</sub> hyperparameter (traditional ML concept) to prevent overfitting.

<br />

### 3. Alternating Optimization & The Sparse Trick

Now that we have our objective function $\mathcal{L}(X, Y)$, how do we actually find the optimal matrices $X$ and $Y$?

<br />

In matrix factorization <sub>[\[19\]](#citation19)</sub>, we are multiplying two unknown matrix variables together ($\mathbf{x}_u^\top \mathbf{y}_i$). This makes the overall loss function **non-convex** with respect to both $X$ and $Y$ simultaneously. If you try to optimize both at the same time using basic gradient descent, optimization is slow and easily gets stuck in poor local minima. \
\
However, notice something special:
<BlogList>
  <li>If you <b>freeze the beatmap matrix $Y$</b>, the objective function becomes a simple <b>weighted linear regression</b> for every user vector $\mathbf{x}_u$ (which is convex and has an exact analytical solution!).</li>
  <li>Similarly, if you <b>freeze the user matrix $X$</b>, solving for every beatmap vector $\mathbf{y}_i$ also becomes a convex linear regression problem!</li>
</BlogList>
<br />

This is why it's called **Alternating Least Squares (ALS)**: we alternate back and forth—holding $Y$ fixed to solve for $X$ in closed form, then holding $X$ fixed to solve for $Y$ in closed form—until the loss stabilizes.

  $$
  \mathbf{x}_u = \left( Y^\top C^u Y + \lambda I \right)^{-1} Y^\top C^u \mathbf{p}_u
  $$
  $$
  \mathbf{y}_i = \left( X^\top C^i X + \lambda I \right)^{-1} X^\top C^i \mathbf{p}_i
  $$

<br />

Now while the closed-form formula above looks simple, there is a performance issue:\
\
$C^u$ is a diagonal matrix of size $M \times M$, where $M$ is the total number of beatmaps in the dataset (tens or hundreds of thousands of maps!). 
Trying to compute $Y^\top C^u Y$ for every user on every iteration requires $O(f^2 M)$ operations. That's...really slow if you have millions of users. 

<br />

<b>Here's the trick:</b><br />
Notice that $C^u = I + (C^u - I)$. We can rewrite $Y^\top C^u Y$ as:

$$
Y^\top C^u Y = Y^\top Y + Y^\top (C^u - I) Y
$$

Now THIS is a game changer. Why?
<BlogList>
  <li>
    <b>$Y^\top Y$ (Global Baseline)</b>: Does not depend on a user. We can precompute $Y^\top Y$ <i>once per iteration</i> for all $M$ beatmaps in $O(f^2 M)$ time and never touch it again.
  </li>
  <li>
    <b>$Y^\top (C^u - I) Y$ (Sparse User Correction)</b>: For user $u$, $(C^u - I)$ is non-zero <i>only for the maps the user has actually played</i> ($n_u$ maps). Since a typical player has only played a small number of maps (a few hundred out of 100k+, $n_u \ll M$), we only multiply over those $n_u$ played maps!
  </li>
</BlogList>

<br />

Substituting this back into the user update formula gives our fast iALS update:

$$
\mathbf{x}_u = \left( Y^\top Y + Y_{n_u}^\top (C_{n_u}^u - I) Y_{n_u} + \lambda I \right)^{-1} Y^\top C^u \mathbf{p}_u
$$

This reduces the time complexity per user from $O(f^2 M)$ down to $O(f^3 + f^2 n_u)$. While $f^3$ still sounds slow, $f$ is only 64. Compared to $O(f^2 M)$, this is a huge improvement!

<span id="als-implementation"/>
## 5. Recommendation Model (Implementation)

Ok, blah blah blah, how does this translate into our backend implementation for serving recommendations?

<br />

### 1. Building the Sparse Matrix & Offline Fitting

First, we query all replay records (`osu_id`, `map_hash`, `mastery_score`) from our SQLite database and convert them into a sparse user-item matrix:

<BlogList>
  <li>Each user and beatmap is assigned a unique integer index.</li>
  <li>As mentioned earlier, confidence weights are assigned as $c_{ui} = 1.0 + \alpha \cdot \text{mastery}_{ui}$.</li>
  <li>We train our global `AlternatingLeastSquares` model with $64$ latent factors over $50$ iterations (with early stopping).</li>
</BlogList>

<br />

After fitting, the learned beatmap factor matrix $Y \in \mathbb{R}^{M \times 64}$ and integer-to-hash mapping dictionaries are saved to disk.

<br />

### 2. On-the-Fly User Vector Refresh (Real-Time Ingestion)

When a player enters their username on the site, we don't want to wait hours to re-train the entire global model across all users.

Instead, when our replay ingestor fetches the player's top plays, we project the player into the 64-dimensional latent space in **real-time** by executing the closed-form update rule directly in NumPy:

<BlogList>
  <li>We extract the played map indices and calculate their mastery confidence weights.</li>
  <li>We compute the sparse correction matrix $Y_{n_u}^\top (C_{n_u}^u - I) Y_{n_u}$ using only the maps the user played.</li>
  <li>We solve the linear system $(Y^\top Y + Y_{n_u}^\top (C_{n_u}^u - I) Y_{n_u} + \lambda I) \mathbf{x}_u = Y_{n_u}^\top C^u \mathbf{p}_u$.</li>
</BlogList>

<br />

Assuming we have enough users that are already in the system, there shouldn't be too many cold-start users. \
\
Remember the **replay dataset** I was talking about before? Yeah, it came in handy here. \
\
Using the replay dataset, I was able to get approximately 300 thousand replays under 30 thousand users. Not bad for a start. \
\
Additionally, because $f=64$ is small, this linear system is solved in under **2 milliseconds**, providing an instant user embedding.

<br />

### 3. Generating Recommendations with L2 Cosine Matching

Once we have the user vector $\mathbf{x}_u$, we score all candidate beatmaps in the library. To prevent maps with larger vector magnitudes from dominating recommendations, we compute **L2-normalized Cosine Similarity** <sub>[\[16\]](#citation16)</sub>:

$$
\text{score}_{ui} = \frac{\mathbf{x}_u}{\|\mathbf{x}_u\|_2} \cdot \left( \frac{\mathbf{y}_i}{\|\mathbf{y}_i\|_2} \right)^\top
$$

We then apply business filters:
<BlogList>
  <li><b>Exclude Played Maps</b>: Remove any map hashes already in the player's replay history.</li>
  <li><b>Comfort Star Rating Filter</b>: Optionally filter out recommendations whose Star Rating (SR) deviates too far from the player's average comfort level.</li>
</BlogList>

<br />

It should be noted that the star rating filter seems to be redundant at the moment, as the model seems to be doing a good job at recommending maps that are within the player's comfort range already!
Of course, if I get feedback that that's not the case, I can simply adjust the sr_tolerance parameter in the frontend to filter out those recommendations.

<br />

### 4. Vectorized "Influential Play" Attribution

One cool feature on the website is showing **which of the player's past plays influenced each recommendation**.

Instead of iterating through every target map one-by-one, we compute this in a single **vectorized batch matrix multiplication** in $\approx 5\text{ms}$:
- We multiply the matrix of target recommendation vectors against the transpose of the user's played map vectors ($\mathbf{S} = \mathbf{T} \cdot \mathbf{P}^\top$).
- We weight the similarity by the player's mastery score on each played map.
- For each recommendation, we return the top 3 most structurally similar played maps to render on the recommendation card!

### 3.2 Asynchronous Job Queue & API Protection

Fetching multiple plays for a user involves multiple HTTP requests to the osu! API, parsing binary `.osr` replay files, computing hit object statistics, and running model inference. \
\
If we executed all of this synchronously inside a FastAPI endpoint request, the HTTP thread would block for several seconds—causing browser timeouts and a terrible user experience. Furthermore, unthrottled requests to `osu.ppy.sh` would risk exceeding strict API rate limits and getting our application IP banned.\
\
(To be honest, I did get rate limited a couple times during initial testing. Sorry peppy.) \
\
To solve both throughput and API rate limiting, I built an asynchronous worker pipeline paired with a multi-tier defense:

<br />

<BlogList>
  <li>
    <b>Non-Blocking Job Enqueueing (Redis Queue)</b>: When a player requests recommendations or recalibration, FastAPI enqueues a job via <b>Redis Queue (RQ)</b> and returns a unique `job_id` in ~2ms. Background workers parse replays and compute vectors out-of-band while the frontend polls `/jobs?job_id=...`. 
  </li>
  <li>
    <b>OAuth Token Caching</b>: Client Credentials access tokens are requested once and cached in memory until near-expiration.
  </li>
  <li>
    <b>Database-First Lookup</b>: Player usernames and beatmap IDs check `DatabaseManager` first, querying external APIs only when records are missing locally.
  </li>
  <li>
    <b>Active Job Deduplication</b>: If a user is already being ingested, duplicate requests check Redis for an active job key (`active_job:topreplay:{uid}`). Subsequent requests attach to the existing `job_id` instead of spawning duplicate API fetches.
  </li>
  <li>
    <b>Replay Threshold Guard</b>: If a player already has $\ge 25$ replays cached in our local database, `/user/replays` immediately serves local data without hitting osu! servers.
  </li>
  <li>
    <b>Redis Payload Caching</b>: Final recommendation payloads are cached in Redis with a 15-minute Time-To-Live (TTL), turning repeat visits into sub-millisecond cache hits. 
    Osu has a rate limit for each individual endpoint, so we need to be careful.
  </li>
</BlogList>

### 3.3 Recommendation Caching & Performance Optimization

Computing recommendations involves matrix operations ($\mathbf{S} = \mathbf{T} \cdot \mathbf{P}^\top$), solving user preference vectors ($\mathbf{x}_u \in \mathbb{R}^{64}$), and extracting top-3 influential play attributions for every candidate map. \
\
While running vectorized NumPy operations takes under $\approx 5\text{ms}$ in memory, re-computing these scores on every page navigation or UI filter tweak is completely wasteful. I implemented a multi-tiered caching architecture to maximize efficiency:

<br />

<b>Caching Architecture & Optimizations:</b>
<br />
<BlogList>
  <li>
    <b>15-Minute Redis Payload Caching</b>: The final serialized recommendation JSON payload (map metadata, similarity scores, and play attributions) is cached in Redis under `cache:endpoint:recs:{uid}:{mods}:{version}` with a 15-minute Time-To-Live (TTL). Repeat visits or page refreshes return sub-millisecond (\&lt;1ms) cache hits directly from Redis without touching Python ML code.
  </li>
  <li>
    <b>User Latent Vector Persistence</b>: Once solved via Ridge Regression, a player's latent vector $\mathbf{x}_u \in \mathbb{R}^{64}$ is stored in Redis under `cache:recs:user_vector:{uid}`. Subsequent recommendation calls reuse this pre-computed vector instantly unless the user explicitly triggers a "Recalibrate" action.
  </li>
  <li>
    <b>In-Memory C-Contiguous Matrix Layouts</b>: Item latent factor matrices ($\mathbf{Y} \in \mathbb{R}^{M \times 64}$) and beatmap VAE vectors ($\mathbf{z} \in \mathbb{R}^{128}$) are pre-loaded at server startup into contiguous C-order `float32` NumPy arrays (`item_factors`, `item_norms`). This enables SIMD-accelerated dot products during L2 cosine matching (`item_norms @ user_norm`) with zero disk I/O.
  </li>
</BlogList>

### 3.4 Containerized Infrastructure & Docker Setup

To ensure seamless deployment, reproducible environments, and single-command local setup, the backend is containerized using **Docker** and orchestrated via **Docker Compose**.

Decoupling the application into isolated containers prevents dependency conflicts between machine learning packages (e.g., PyTorch, Implicit, SciPy, NumPy) and the async web layer while allowing scaling of background worker tasks.

<br />

<b>Docker Services Architecture:</b>
<BlogList>
  <li>
    <b>FastAPI Container (`web`)</b>: Runs the Uvicorn ASGI server hosting all API routes. Handles lightweight requests, user vector projections, matrix multiplications, and static asset delivery.

  <li>
    <b>Redis Container (`redis`)</b>: Serves as the shared message broker for Redis Queue (RQ) and acts as an in-memory cache for 15-minute recommendation payloads and OAuth tokens.
  </li>
  <li>
    <b>RQ Worker Container (`worker`)</b>: Executes background task workers isolated from the main web process. Consumes jobs from Redis to perform heavy binary `.osr` replay parsing, VAE map tensor generation, and database updates.
  </li>
  <li>
    <b>Database Container (`db`)</b>: Houses persistent storage for player profiles, map metadata, and trained latent factor matrices ($X$ and $Y$).
  </li>
